# The prover on a Tinfoil H200: phase 1 (inventory and an untested draft package, nothing run)

**Status: nothing has been run on the H200. This is an untested draft package, not a ready one.** This directory has a container image recipe, a draft Tinfoil config, a job runner, a read-only results server and a runbook for running the upstream small synthetic example on one H200 in a Tinfoil enclave, with the same protocol as the H100 receipts (`research/gpu/`). Phase 1 read the platform's docs and the org's own state with read-only calls and built the first stages of the image. It created, changed and stopped nothing on Tinfoil. The runner's and the server's control flow is tested on CPU with mocked GPU programs (`run_job_test.py`, `serve_test.py`); nothing here has run on a GPU. (Phase 1 built only the first image stages; since issue #140 every stage has been built locally and nothing has been pushed: section "Issue #140" below.) Phase 2, the run itself, waits for the decisions below. The protocol for phase 2 is registered in advance in `experiments/20261110-43-h200-bringup/PREREG.md`.

Part of #43 (item 4: H100 control vs a larger-memory GPU) and #7 (cost). Changes after the independent review of the first version are listed in the PR and in `experiments/20261110-43-h200-bringup/RESULTS.md`, "Changes after review".

## What is proved, what the verifier recomputes, what is not covered

Same as `research/gpu/`: the example commits to synthetic ("made-up") weights of the small configuration `target_small_f2_roomy`, proves one request (`own_choices.req`) and checks the proof. `cp_verify` recomputes, from public files alone (the configuration, the key file and leaf entry, the request, the answer and the proof) and the commitment ID, that the answer is the committed model's output on that request at the covered positions. Not covered here: real weights, the full-size configuration, Qwen, batching, serving, and anything about the enclave itself. A Tinfoil attestation would say which image and config ran; it does not replace the proof, and the proof does not depend on it.

## The answers phase 1 found

**Can two containers share one GPU?** Not as two instances. Each Tinfoil instance is its own confidential VM with whole GPUs passed through to it (the live instance runs on AMD SEV-SNP; the platform also supports Intel TDX), and in NVIDIA's confidential-computing model a GPU is assigned to one VM. NVIDIA's r580 release notes exclude MPS in CC mode; we did not find an explicit no-MIG statement in the saved sources. Containers inside one instance can share its GPU (the live instance already runs two model servers on it).

**How many GPUs does the host have? Not established.** The saved read-only evidence shows: one GPU host surfaced to the org, and the live instance assigned one GPU. The host's `available_gpu_values: [1]` is, per the platform's admin API docs, the intersection of the host's capabilities and the org's entitlement, that is, a permitted instance shape. It is not a count of installed or idle cards. A read-only validation and an update plan are not capacity reservations and say nothing about a free second GPU. So whether a second instance with a GPU could boot beside the live one is an open question for the owner (and the provider). Evidence that would settle it: the provider stating the host's installed and free GPU count for the org, or a host listing that reports it; an attempt to create an instance would also answer it, but that is a write and is not done here. Everything that follows from "one GPU" is conditional:
- **If the host has no second free GPU** (assumption, not established): no second instance with a GPU can boot while the live instance runs, in production or debug mode; a single-GPU blue/green update of any instance is refused with `HOST_GPU_BUSY` (platform docs); the options are (A) stop the live instance for a proving window, which means downtime, (B) add the prover as one more container inside the live instance's config, which changes the measured config of a live service, or (C) a second host.
- **If the host has a second free GPU**: the prover could run as its own instance beside the live service, with no downtime for it, provided the org may run a second GPU instance. RUNBOOK.md, step 0, asks this before anything that stops the live service.

**What fits beside the live service?** Nothing, without changing the prover. The platform's metrics for the live instance report GPU memory in use as an integer percentage of a reported total of 140 (the response does not state the unit, GB or GiB). The 24-hour response has 30 buckets, all 30 at 94 %. The 7-day response also has 30 buckets: 20 with total and utilisation both 0 (no data), then one at 87 %, one at 93 % and 8 at 94 %, about 2.3 days of data, not seven. At 94 % of 140, nominally about 8.4 of the reported units are free; that is a derived figure from rounded percentages, not a measured free-memory value. `cp_commit` and `cp_prove` in the default build refuse to start when more than 2 GiB of the GPU are already in use (`prover/common/common.h`, `GPU_IN_USE_AT_THE_START`), because they assume the GPU is theirs alone. Even in a test build, which only warns, `cp_commit` keeps 2 GiB plus 24 GiB for its engine and 1 GiB of slab spare free beside its main buffer (`prover/hash_commitment/hf_commit_once.cuh`, `HF_ONCE_ENGINE_ROOM`), so it needs at least about 27 GiB free at the small size. That is a lower bound from the sources, not a measured fit. On the H100 it took 74,165 MiB only because it sizes its buffer to what is free; the prove window peaked at 5,293 MiB (`research/gpu/README.md`). So the small example does not fit in what the live service leaves; the prove step alone would, but it needs a commitment made first.

**Confidential-computing mode is a second blocker, predicted from the sources.** Both programs page-lock host memory with `cudaHostRegister` and treat a failure as fatal (`hf_commit_weights.cuh`, `hf_open_side.cuh`, `hf_keeper.cu`, `weight_stream.cuh`). NVIDIA's Trusted Computing release notes (r580, "Limitations in the SPT CC and PPCIe Modes") list `cudaHostRegister` as not allowed in CC mode, and a public vLLM report measured error 801 on an H200 in CC-On while `cudaHostAlloc` worked. The live instance runs with confidential computing on (`disable_cc_mode: false`). Phase 1 recorded a CLI flag `--disable-cc-mode` described as experimental, for benchmarks only and requiring an org entitlement; **that wording and the entitlement are unverified**: the independent review did not find them in the saved CLI and admin API docs, and whether this org has such an entitlement is not visible from read-only calls. So in a normal (CC-On) Tinfoil enclave the unmodified prover is expected to stop at its first `cudaHostRegister`. The image includes `cc_probe` to check this in the first second of the run. A fix in the prover (allocate with `cudaHostAlloc` instead of registering) is a code change, outside this lane. This is the decision that matters most.

**Cost of CC mode.** NVIDIA's numbers: GPU compute and HBM bandwidth at par; CPU-GPU transfers go through encrypted bounce buffers, about 4 GB/s (NVIDIA developer blog, 2023), about 4.9 GiB/s measured for `cudaHostAlloc` copies in the vLLM report. At the small size the weights are tiny, so the effect should be small. At full size the prover streams weights from host memory every pass, so the effect could be large. Not measured.

**Getting a job in and results out.** Production instances have no SSH. Debug instances do (`tinfoil container create --debug --ssh-key`, then SSH into a toolbox), but they do not attest and still take a GPU. Direct admin SSH needs `cvm_admin: true`, which grants control of the whole enclave. The package here uses neither: the job runs once at boot, and a read-only HTTP server behind the attested shim offers `/status`, `/files` and `/results.tar.gz`, fetched with `tinfoil http get` or `tinfoil container connect`. No request can start or change a job. The job's results are finalised and stay served whether the job succeeds, fails or times out (a TERM or INT signal to the entrypoint itself finalises the results and then stops the server too, as a shutdown should), and a failure while finalising (an export, the marker, the checksums) ends as `FAILED` with a stage line naming the step, never as `DONE` (`run_job.sh`, header). One job per work directory: a second start is refused (a `flock` lock). That lock is advisory: it excludes cooperating starts of the runner on the same lock file and assumes a private local work directory (the config's mode-0700 tmpfs, used by one container) with working `flock`; a process that writes there without taking the lock, or replaces the lock file's inode during a job, is out of its scope. `isk/` (the commitment's secret side) never leaves the work directory, which is a tmpfs inside the enclave and is gone when the instance stops.

**What is exported, and duty 6.** For every run the public configuration, key file, request and the programs' logs are exported. A run's response (`out/`) and its `cp_verify.log` are exported **only if `cp_verify` accepted the run** (exit 0 and `YES`). For a run that was rejected, crashed, timed out or was stopped before it was checked, they are withheld: their names go to `<run>/withheld.txt` and they are removed with the work directory, as `docs/limits.md`, duty 6, requires ("let no response leave you before `cp_verify` has accepted every proof"). The run's verdict line is still in `<run>.verdict`. The weights here are synthetic, so nothing real would leak, but the package follows the repo's operator rule rather than making an exception to it.

**File boundary of the server.** `serve.py` opens the results directory once and opens everything else relative to a descriptor inside it, one path component at a time, never following a symbolic link (`O_NOFOLLOW`, `O_DIRECTORY` for directories, `fstat` of every opened object: a directory or a regular file only). A parent directory replaced by a link between a check and an open, at any depth, therefore cannot lead it outside the results directory; the tests swap one at each depth. Connections are bounded (16) before a handler thread is started; a request line over 64 KiB gets 414.

<a id="where-the-config-lives"></a>
**Where the config lives.** Tinfoil reads `tinfoil-config.yml` from the root of a public GitHub repo that has the two Tinfoil release workflows, and releases are tags of that repo. The config repo must be public; the image need not be (private images with registry credentials are allowed, platform docs "Private images"). `wakesync/flashprove` is public, but putting the config at its root and adding release workflows that create tags would mix research tags with enclave releases in the main research repo. Recommended: a small separate public repo made from `tinfoilsh/tinfoil-containers-template`, holding only `tinfoil-config.yml`, the image build and the release workflows, with the image built from a pinned `wakesync/flashprove` commit. That needs a new repo, so it is a decision, not something this lane did. The alternative (config at the root of `wakesync/flashprove` plus the two workflows) works and needs no new repo, but every enclave release would then be a tag here.

1. Which window: (A) stop the live instance for a proving window, (B) put the prover inside the live instance, or (C) a second GPU, on this host or another.    B is not runnable as the package stands: besides lowering the engines' memory share, the default prover refuses a GPU with more than 2 GiB in use, so B also needs a prover change or a test build, which is outside this lane and would be a registered deviation.
2. CC mode: ask the provider whether a CC-off benchmark mode exists and is enabled for the org (the flag wording recorded in phase 1 is unverified), or accept that phase 2 may first only measure the predicted CC-On refusal and then wait for a prover change that avoids `cudaHostRegister`.
3. Where the config lives: a new public config repo (recommended) or the root of this repo.
4. The image: a public GHCR package is the simplest choice (no registry credentials to manage) and is the recommendation; a private image with registry credentials is also allowed. Either way it is a publication decision for the owner.
5. `FP_ONBOX_BUILD`: 1 (the default, the PREREG's cold run: the quickstart rebuilds the programs, about 20 min more of the window) or 0 (the image's prebuilt programs, a shorter window, and a registered deviation from the PREREG).

Downtime, recovery and exact commands for each: RUNBOOK.md.

- `requirements-cuda.txt`: the hash-pinned toolkit wheels.
- `fetch_bounded.sh`: the one helper both of the runbook's fetch paths use (step 5): one clock read, budget = cut-off minus now minus the kill grace minus a launch margin, the fetch run under `timeout -k <grace> <budget>` only if that budget is strictly positive, otherwise not started (exit 121). So a fetch is over before the restore cut-off even if it ignores TERM, and a zero duration (no timeout, for GNU `timeout`) is never passed. Before any arithmetic it refuses (exit 2, nothing started) grace or margin that are not canonical decimals from 1 to 3600, a cut-off or clock reading that is not 10-digit epoch seconds between 2001 and 2100, and a cut-off more than 6 h ahead, so no value can wrap or be read as octal. The bound assumes a synchronised clock (the window sheet's NTP check), launch delay within the margin, and a fetch that stays in its process group (RUNBOOK.md step 5); it is not a hard real-time guarantee. `fetch_bounded_test.py` tests it on CPU: it takes both fetch commands out of RUNBOOK.md, puts an inert local program in place of the fetch, and checks a clock that moves from 1 s to 0 s left between reads, a cut-off already reached or passed, less time left than the kill grace, a fetch that ignores TERM (by the wall clock it must be over by the cut-off) and a fetch with time enough, plus the input bounds (grace = margin = 2^63-1 at the cut-off, a clock printing 2^64-1 or 2^63, out-of-range and negative clocks, `08`, `010`, `-0`, `+5`, whitespace, values over 3600, a cut-off more than 6 h ahead); `--runbook <file>` runs the path cases against another version of the runbook, `--helper <file>` the helper and bounds cases against another version of the helper.
- `RUNBOOK.md`: the window sheet the owner fills in, bring-up, the baseline run, result retrieval, teardown, restoring the live instance, recovery if restore fails, and checking that it serves again.
- `verify_offbox.py`: RUNBOOK.md step 8, the off-box CPU verification of every expected response of every expected run (the #43 runs' `example`, each calibration run's r01..rNN), against each run's own commitment ID, fail-closed (a missing run or response, a withheld `out/`, a rejection anywhere in a batch, or an unexpected file fails the run; overall PASS only if every run passed), plus the five registered mutation cases. The expected runs come only from the registered values on its command line (`--plan '<FP_CALIB>'` or `--no-calibration`, and `--repeats`, all required), never from the archive: a missing, empty or different `results/calib-plan.txt`, a run the registration did not name (directory, `steps.tsv` row or run file), a missing `steps.tsv` and a missing or mismatching `SHA256SUMS` each fail the whole check. `verify_offbox_test.py` tests it on CPU with a mocked verifier (`verify_offbox_test_mocks/cp_verify`), including a batch whose r01 is rejected while r02..r08 pass and the round-2 review reproductions of PR #141 (missing or shortened archive plan, deleted calibration runs, extra C2-4/C3-4/rep11, a `--repeats` lower than the job's), each of which must FAIL.
- `image_contract_test.py`: static check (no docker) that the config's healthcheck executable is installed in both the `final` and the `runtime` stage, that it targets the server's port and path, that the command itself succeeds against `serve.py` locally, that `final` is the last stage and that the stage/`FP_ONBOX_BUILD` pairing holds.
- CI: `.github/workflows/h200-package-tests.yml` runs the six test files (`serve_test.py`, `run_job_test.py`, `run_job_calib_test.py`, `fetch_bounded_test.py`, `verify_offbox_test.py`, `image_contract_test.py`), `bash -n` and shellcheck of the four shell scripts (`run_job.sh`, `fetch_bounded.sh`, `calib_run.sh`, `stamp.sh`) on every PR that touches this directory or the workflow, and on pushes to main that touch either.

The **`runtime` stage** is the variant for a public image: it ships the programs (our application) and only the three runtime libraries they load (`ldd`, checked against Attachment A in the build, unmodified files), no compiler, no headers, no static libraries, no driver stub. A private `final` image with registry credentials for the org keeps the on-box build and avoids the question.
