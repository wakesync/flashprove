# Per-tensor binding in a research key file

Part of #36. Registration: [PREREG](../../../experiments/20261111-36-keyfile-tensor-binding/PREREG.md).
This is the existing CPU **small-key fixture**, not a new stand-alone hash demonstration and not
production `cp_verify`. The fixture is `blocks/frame/tests/small_key_test.cpp` and
`blocks/iop/tests/wf_small_world.h`: a four-by-four matrix, four named row tensors, entries in
[-2, 1], a complete range proof and the three native key chains (WF, BATT, LIN, proximity tests).
It uses the fixture's hand-written test plans. **No soundness level, hiding guarantee, Qwen proof,
or production model-support claim follows.**

## What is checked inside the proof

`manifest.h` implements the non-circular order of `research/weight-binding/DESIGN.md` 2.0/2.2:

1. Checkpoint ID: the existing `wb_manifest.py` SHA-256 Merkle algorithm over four sorted leaves,
   each (name, I64, [4], SHA-256 of signed little-endian tensor bytes). Field residues are mapped
   back to signed source integers, not hashed as their field spellings.
2. Conversion ID: a separate **small-key** domain binds that checkpoint, identity-conversion
   version, the fixture configuration digest, each row's name/address/length/exponent and both
   source-leaf and integer-byte hashes. This is not Qwen `wb_conv.py`'s schema.
3. After committing the actual table, compute its **native `published_id`**, including configuration,
   root, shape, OOD record seeds and record answers. Derive each tensor's two-coordinate point
   from `fp-wb-point-v2`, that ID, the conversion ID, length-prefixed name, coordinate index,
   extension-field limb and rejection counter. SHA-256 yields each base-field coefficient by
   rejecting 64-bit candidates >= the Goldilocks prime; three coefficients make one cubic element.
   Neither expected evaluation nor proof output enters either manifest ID.
4. Add one `TensorRow` per tensor to the range proof's pending rows. Its row weights are the
   verifier-fixed unit vector for that tensor's row; its column weights are the equality polynomial
   at the derived point; its target is the verifier's MLE of the public expected integers.
   BATT combines the existing two range claims and four new claims. LIN proves that combined claim
   against the **same original committed table**. There is no separately committed witness.

`key_adapter.h` is generated by `generate_adapter.py` from `blocks/frame/check_key.h`. The changes
are a distinct one-time chain label, a bound manifest input, and the extra pending rows on both
sides. All native proof checks and session-finalization checks remain. The research return type
is an `IndexKey`, never a production `TestedTable`. Shared/second chains remain bound to the first
chain's seal. Rebuilding the fixture's first plan counts six pending claims rather than two;
BATT's mask count depends on the two column bits, not the claim count. These test plans provide
no production error-accounting result.

## Key format and verifier trust

The research file is `FPWB` (four bytes), u32-LE extension version 1, checkpoint ID (32 bytes),
conversion ID (32 bytes), followed by the native key serialization with the extended first chain.
The envelope is 72 bytes. The native format/version is still checked inside it. Targets are
**recomputed, not serialized**. There is no claimed general-purpose format parser for manifests.

The verifier receives the expected public integers, names, configuration and the two held IDs
from its caller. It checks their consistency and canonical order before native verification.
It never reads expected tensors from a proof. Both held IDs enter the first chain's statement.
The untrusted envelope IDs are checked only **after** the native proof: replay under another
valid held manifest must exercise the native checks, not merely an outside header comparison.
The local API assumes trusted caller-sized fixed fixture parameters, like the upstream fixture.

The first three hostile arms commit in-range substituted tables but bind the original manifest.
A test-only dishonest prover changes its own pending claim targets to evaluations of those
substituted tensors, allowing complete malicious proof files to be emitted. The verifier has no
such switch. A one-tensor replacement changes one element of row 0; two replacements also change
one element of row 2; the order attack exchanges complete rows 0 and 1 while names/addresses stay
fixed. Paired legacy proofs show those tables still satisfy the original unbound key statement.
The other-checkpoint and conversion-ID arms replay an otherwise valid key under a different,
self-consistent held statement, with honest alternate controls. Malformed/stale manifest and
header tests are separate debug tests, not counted as these native-proof negatives.

## What is not established

- No production key.bin/cp_commit/cp_verify integration, no served request/reply proof here.
- No Qwen tensor placement, conversion, WF layout, full-size key, or proof reaching changed layers.
- No claim to detect abliteration in a proof. Qwen has 1,199 source tensors but the existing design
  has 722 effective **text** blocks; visual/MTP tensors are outside that proof design.
- No Fiat-Shamir/grinding bound, security level, hiding proof, or formal soundness result for this
  adapter. Test coins and tiny hand-planned fixtures are not production parameters.
- The caller must obtain the expected checkpoint/manifest from a trusted source. Hidden-weight
  signed evaluations and arbitrary tensor shapes are not implemented.
- Counts of large-model work are counts only. Neither large-model proof size nor verification time
  is extrapolated from the tiny fixture.

## Reproduce

From repository root, g++ 13 and Python 3 standard library. No GPU, external library, or download.
Every output directory/file must be fresh. On shared hosts run suite/debug/replay through the
host's heavy-job gate, pinned to your assigned cores. The registered lane used cores 10-12.

```sh
python3 research/weight-binding/keyfile/run.py build --out /tmp/keybind-build
python3 research/weight-binding/keyfile/run.py debug --out /tmp/keybind-debug
python3 research/weight-binding/keyfile/run.py suite --out /tmp/keybind-runs
python3 research/weight-binding/keyfile/replay.py --runs /tmp/keybind-runs --binary research/weight-binding/keyfile/work/test.bin --out /tmp/keybind-replay.json
python3 research/weight-binding/keyfile/run.py summary --out /tmp/keybind-runs
python3 research/weight-binding/keyfile/count.py --out /tmp/keybind-count.json
```

The suite uses coins 1001..1010, alternates legacy/bound verification order, and reports every
measurement. The debug fixture uses 9001, different names and different values. Honest paired
controls reuse the original key for that seed; those repeated controls are not independent new
proofs. `run.py` enforces a 35-minute gate-grant budget; `--enforce-deadline` additionally enforces
the original lane deadline (omit it for later reproduction).

To verify saved files without regenerating them, the caller explicitly chooses the expected
fixture. It never chooses an identity from the supplied key's header:

```sh
research/weight-binding/keyfile/work/test.bin verify /tmp/keybind-runs/seed-1001/bound-honest.key 1001 original bound
research/weight-binding/keyfile/work/test.bin verify /tmp/keybind-runs/seed-1001/one-tensor-swapped.key 1001 original bound
```

Expected exits: 0 for the honest key, 1 for the complete substituted key. `other` and `conversion`
choose the alternate trusted fixtures; `legacy` checks the original unextended key format.
The CLI caps supplied key files at 8 MiB. It is a test verifier, not a production interface.

For UBSan, build with `--ubsan --binary /tmp/keybind-ubsan.bin`, then run debug with that binary.
The Python runner independently recomputes checkpoint leaves/roots using `hashlib` and the merged
`wb_manifest.py`. `cache_probe.py --root <local-cache> --out <fresh.json>` only inspects local
safetensors availability; it never downloads or substitutes old hash receipts for a fresh rehash.
