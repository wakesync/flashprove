# PREREG: 20261111-95-fs-grinding
Issue: #95. Lane: grind95. Date (UTC): 2026-11-11T09:35Z. Base commit: 7c40dd9fc728ab99d1659dc47af59c9d53e67107.

## Hypothesis
On the research toy profile of the bounded Qwen operator relations (convolution, F = 12, research target 10 bits with 6 bits of proof of work on the query rounds, `research/operators/qwen_ops/proof.cpp`, merged with PR #67), a prover that grinds the Fiat-Shamir hash chain at the planned round with the largest error before work (a round that draws positions) gets an accepting draw of positions at a rate per completed try that is consistent with the uniform-draw figure p0 = (A/n)^t, and not above the plan's error bound e for that round; so grinding buys nothing beyond paying for more tries, and the cost of one accepting draw is about 2^w / p0 nonce tries.

## Metric
The harness (to be written after this file, under `experiments/20261111-95-fs-grinding/`) plans the profile with the unmodified library and takes the round class with the largest error without work among rounds of kind POSITIONS, the class that `blocks/numbers/accounting.h` reports as `lists` if that is a POSITIONS round. From the plan it reads t (positions drawn), log2 n (range of each position), w (work bits) and e (the round's whole error bound, work not counted). It sets a = e^(1/t) and A = floor(a n): the cheating prover's committed word agrees with the codeword nearest to it on a fixed set S of A of the n positions (S = {0, .., A - 1}; draws are uniform, so the choice of set does not matter). For a round priced as agree^t, a is the analysis' agreement; for a round whose bound has an extra batching term, a is above the agreement, which favours the attacker. A draw "forges" if all t positions lie in S.

Each try uses the library's own hash chain (`blocks/chain/chain.h`: `ChainT`, `chain_call`, `work_test`, `draw_position`), a query prefix built with `Chain::message()` and `Chain::prefix(.., ChainKind::POSITIONS, w)`, a nonce that passes the work test, and the t positions drawn from that answer exactly as `PositionsDraw::positions` draws them.

What the prover controls and the harness re-randomises: (i) the nonce (any nonce that passes the work test is valid, not just the first); (ii) its own message before the draw, standing for a re-commitment with fresh private coins (salt and masks), which changes the Merkle roots and so the query prefix. Nothing that the verifier fixes (label, round number, kind, work bits, prior chain value) is varied beyond what a re-commitment changes.

Measured per run: tries (completed draws, nonces that passed work), forges, nonces tested (each one hash call of the work test), forge rate = forges / tries, nonces per forge. Pooled over runs: exact Clopper-Pearson interval at 99% on the forge rate.

## Acceptance threshold
PASS if, for each grinding arm (A and B below), the pooled 99% Clopper-Pearson interval on the forge rate contains p0, and its upper end is at most e x 1.05 (a 5% margin for sampling at the planned n). Plus a check reported but not a pass/fail gate: pooled nonces per forge within 10% of 2^w / p0.
FAIL if an arm's interval lies wholly above p0, or its upper end exceeds e x 1.05: grinding beat the per-round figure on this round, which is a finding to report. An interval wholly below p0 is also reported as FAIL (the draw is not uniform as assumed).

## Runs
Arm A, nonce grinding: one fixed prefix per run, consecutive nonces from a seeded random start, every nonce that passes w work bits is a try. Arm B, message grinding: for each try a fresh 32-byte prover message (seeded generator) is absorbed, the first nonce from 0 that passes work is taken. Arm C, control: arm B with w = 0 (no work), to show the 2^w factor in cost. n = 5 runs per arm, seeds 1..5, each run 100000 tries (so 5 x 10^5 tries per arm). No warmup (the measure is a count, not a time); wall time is recorded for information only. Nothing is excluded. Raw per-run JSON lines are committed under `runs/`. Debugging of the harness is done on a different round (the plan's first POSITIONS round of another class, or the toy product run of `blocks/toy/toy_main.h`) with 1000 tries and seed 99, never on the registered round and seeds before the registered runs.

## Prior art
Grinding as an attack on Fiat-Shamir compiled IOPs and its mitigation by proof of work: Starkware, "ethSTARK documentation", ePrint 2021/582 (grinding factor, Theorem 6), which `accounting.h` cites for counting g bits of work as 2^-g. Round-by-round soundness as the property that makes a Fiat-Shamir compilation resist grinding by a prover that makes t hash queries, with error about t times the largest round error: Canetti et al., STOC 2019; Ben-Sasson, Chiesa, Spooner, ePrint 2016/116; Chiesa and Yogev, "Building cryptographic proofs from hash functions". Attacks that do succeed exploit weak Fiat-Shamir (statement not hashed), not grinding of a sound round: Dao, Miller, Wright, Grubbs, ePrint 2023/691; this repository's chain hashes the statement into the first query. Practical grinding budgets in deployed systems (Plonky2/Plonky3, Stone, Winterfell use 16 to 20 bits of proof of work with query counts set by a conjectured or proven per-query error); STIR (ePrint 2024/390) and WHIR (ePrint 2024/1586) set parameters round by round. zkML systems (EZKL, zkLLM, Jolt, Expander) inherit their backend's analysis and publish no grinding measurement that we know of. What is new here: a measurement, with the repository's own chain and draw rules, of the forge rate a grinding prover achieves on this protocol's weakest round at the research target, against the plan's own figure. It is not a whole-proof soundness figure and not a security level: it measures one attack on one round of one research profile.

### 2026-11-11 (RETROSPECTIVE, written after the registered runs, in the fix lane for PR #113 review round 1)
This entry was written after the registered runs and their results were committed (receipt commit 9e172eb4). It is a record of a deviation, not a pre-registered change.

1. **Message size in arms B and C.** `Runs` above registers, for arm B, "a fresh 32-byte prover message" absorbed on each try, with arm C as arm B without work. The harness as written and run (`grind.cpp`, commit 7d733084) does not do that. On every B and C try it regenerates the selected round's full planned message, 1590 random words (12720 bytes), and absorbs all of it, so the query prefix has the length a real prover's message at this round would have. When: the change came in with the harness (commit 7d733084, after this file was committed and before the registered runs in 9e172eb4). Why: the producer lane's notes do not record a reason; the effect is that the absorbed message has the planned length of the prover's message at this round (the same length arm A uses for its fixed prefix), rather than 32 bytes. It was not recorded here at the time, and RESULTS.md wrongly said there were no other deviations. It is disclosed now because the independent review at head 97d4213a pointed it out. The acceptance threshold, the metric, the arms, the seeds and the try counts are unchanged, and no registered run was repeated or replaced. Whether a 32-byte message would give a different rate was not measured.
2. **Header time.** The header above says "Date (UTC): 2026-11-11T09:35Z", but the commit that added this file alone (5b89ea5d) is timestamped 2026-11-11T09:29:28Z. The commit time is the real one; the header time was written by hand and is 6 minutes late. The header is left as committed and history is not rewritten.
